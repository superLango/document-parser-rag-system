## 1. 阶段定位

hansonDoc_RAG 作为代码与设计来源：前端按业务取舍做优化改造，后端按前端最终功能完善；能复用的代码审计后迁移，不需要的代码删除。本阶段在写平台代码之前，先确定：

1. 前端到底要哪些功能、不要哪些功能；
2. 前后端代码放在当前项目哪个结构里；
3. hansonDoc_RAG 哪些模块可迁移、哪些需改造、哪些删除；
4. 已知 bug/安全风险是什么，如何避免带病迁移；
5. 以最终前端消费为准的引擎 API 契约草案。

本阶段不写业务代码，只产出决策与骨架。

## 4. 前端功能取舍

先回答“术语集等功能是否还需要”。

| 模块/页面 | 取舍 | 理由 |
|---|---|---|
| 登录/RBAC/审计 | 保留 | 内部使用、可追溯 |
| 知识库/工作空间/群组 | 保留/完善 | 业务确认不简化，后续继续完善 |
| 文档上传/列表/进度 | 需要 | 核心入口 |
| 原文档预览/版面框/Markdown | 需要 | 证据回读 |
| 标准拆分结果（项目/记录/条款/证据） | 新建 | 核心产物 |
| 复核/new 项确认 | 需要 | 业务闭环；单角色 |
| 任务中心/缺口展示 | 需要 | 可运维 |
| 业务词典/别名管理 | 需要（允许人工别名/pending） | 业务系统为主数据源 |
| 旧术语集多源管理 | 不需要 | 不做 api/db 三源编辑器、批量编辑、审核 UI |
| 抽取配置（Schema/类别/Prompt/脚本） | 不需要 | 配方/覆盖模板用配置，不做复杂 UI |
| RAG 问答/图谱/向量搜索 | 不需要 | 不属于标准拆分 |
| API Key | 需要 | 外部对接 |
| 邀请/成员 | 保留 | 知识库协作需要 |
| 帮助/关于 | 可选 | 后置 |

产出 `docs/frontend-scope.md` 与 `docs/frontend-modification.md`：
每个模块必须有“保留/改造/删除 + 理由 + 优先级”，改造项列出需要调整的页面/组件/接口。
该清单是后端完善的输入，**前端驱动后端**。

## 6. 代码审计

### 6.1 审计对象

只审计**确定要迁移/复用的模块**：

- hansonDoc_RAG `backend/app/services/parsekit/`；
- `document_service`/`tasks`/`outbox`/`arq`/`storage`；
- `rbac`/`security`/`audit`；
- `glossary`/`term_base`（改造为业务词典）；
- `integration`/`integration_service`（改造）；
- `frontend/src` 中保留/改造的页面与组件。

不迁移的模块（41 类抽取、`table_to_rows`、chunker/检索、RAG/图谱）直接删除，不做审计。

### 6.2 审计项

- 功能正确性：状态机、幂等、失败回写、并发；
- 安全：认证、越权、文件上传、路径注入、密钥、RLS；
- 数据：迁移、事务、删除/清理、证据存储；
- 依赖：漏洞、许可证、版本锁定；
- 代码质量：重复、异常吞噬、硬编码、无测试。

### 6.3 已知问题（必须确认/关闭）

- `integration` 端点无认证、superuser 绕过 RLS；
- `return_type=object` 未实现；
- `table_to_rows` 不做 rowspan/colspan；
- 大表 chunk 切碎、检索决定完整性；
- 41 类固定类别 + 检索式抽取；
- `match_record` 语义优先 + 阈值硬编码；
- 术语集同步“清空重导”丢审核状态；
- 任务失败重试/状态回写不一致。

产出 `docs/hansonDoc_RAG-audit.md`，结论为“迁移/改造/删除”，高风险=0 才进入 M1.9。
