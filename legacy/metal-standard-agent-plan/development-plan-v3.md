## 0. 本版改了什么

v3.0 不推翻 v2.0 的抽取主线，重点解决四个落地问题：

1. **平台改造**：hansonDoc_RAG 作为代码与设计来源；前端按业务取舍做优化改造，后端按前端最终功能完善；可复用代码审计后迁移，无用代码删除；所有代码在当前项目下。
2. **格式自适应**：把“每份文件打补丁”升级为“表型配方 + 列绑定 + 配置驱动”，新增格式优先改配置，不写代码。
3. **业务对齐**：新增业务主数据对齐层，项目/试验方法命中业务系统则复用，未命中标记新项目/新方法，不静默新建。
4. **环境分工**：1.35 只跑模型（GLM-OCR、PP-DocLayoutV3、Qwen），不承载业务库、队列、Web 服务。

新增里程碑：

```text
M1.5 引用图谱 + 困难表（收尾）
  → M1.6 表型配方 + 列绑定
  → M1.7 项目发现 + 全文档覆盖（原 M1.7 扩展）
  → M1.8 业务主数据对齐
  → M1.9a/M1.9 需求确认/前后端取舍改造
  → M2 数据与微调
  → M2.5 配方运营与冷启动
  → M3 Agent 编排
  → M4 人机协同
  → M5 生产化
```

## 2. 总体架构与环境分工

### 2.1 三平面

```text
┌────────────────────────────────────────────────────────────┐
│ 平台平面：hansonDoc_RAG（应用服务器）                        │
│ React 前端 │ FastAPI │ PostgreSQL/pgvector │ MinIO │ Redis/arq │
│ 文档上传/预览 │ RBAC/知识库 │ 任务中心 │ 术语集 │ 复核/对接     │
│ parsekit：PDF→版面→GLM-OCR→Markdown/layout                  │
└───────────────────────────┬────────────────────────────────┘
                            │ HTTP（标准拆分任务）
┌───────────────────────────▼────────────────────────────────┐
│ 引擎平面：metal-doc-agent（应用服务器，无 GPU）              │
│ TableGrid → 列绑定 → 项目清单 → 记录/条款                    │
│ 引用图谱/跨标准 → 覆盖审计 → 业务主数据对齐                  │
│ API/worker │ 配方注册表 │ 证据链 │ 评测                       │
└───────────────────────────┬────────────────────────────────┘
                            │ HTTP（OpenAI 兼容）
┌───────────────────────────▼────────────────────────────────┐
│ 模型平面：1.35（只跑模型）                                 │
│ GLM-OCR 9977 │ PP-DocLayoutV3 9978 │ Qwen3.5-9B 9989         │
│ 可选 Qwen3.5-35B 9988；无业务库/队列/Web 服务                 │
└────────────────────────────────────────────────────────────┘
```

### 2.2 边界约定

- 1.35 只允许：模型权重、vLLM/推理进程、模型日志、模型启动脚本。
- 1.35 不允许：业务数据库、Redis 业务队列、FastAPI 业务服务、前端、定时业务任务。
- 平台平面负责“文档与流程”，引擎平面负责“标准拆分”，模型平面负责“推理”。
- 引擎不直接读平台数据库；通过 HTTP 契约交换任务、结果、证据。
- 平台不实现 TableGrid/记录抽取；只做上传、预览、任务、复核、展示。

## 3. hansonDoc_RAG 迁移、改造与审计策略

> hansonDoc_RAG 作为**代码与设计来源**：能复用的迁移，需改造的改造，不需要的删除。
> **任何迁移/复用的代码必须先做代码审计，修复已知 bug 后再进入当前项目。**
> 前端先按业务取舍做优化改造；后端按前端最终功能完善；所有代码落在当前项目。

### 3.1 前端功能取舍与改造

| 模块/页面 | 取舍 | 理由 | 处置 |
|---|---|---|---|
| 登录/RBAC/审计 | **保留** | 企业内使用、可追溯 | 迁移代码 + 审计；保留知识库隔离 |
| 知识库/工作空间/群组 | **保留/完善** | 业务确认不简化，后续继续完善 | 迁移 + 审计；不做项目级裁剪 |
| 文档上传/列表/进度 | **保留** | 核心入口 | 迁移 + 审计；增加标准拆分任务类型 |
| 原文档预览/版面框/Markdown | **保留** | 证据回读 | 迁移 + 审计；增加证据标签 |
| 标准拆分结果（项目/记录/条款/证据） | **新建** | 核心产物 | 在当前项目新开发 |
| 复核/new 项确认 | **改造** | 业务闭环 | 迁移交互 + 改造字段/流程；单角色 |
| 任务中心/缺口展示 | **保留/改造** | 可运维 | 迁移 + 增加引擎状态 |
| 业务词典/别名管理 | **新建/改造** | 业务系统为主数据源；允许人工别名/pending | 替代旧术语集编辑器 |
| 旧术语集多源管理 | **删除** | 不做 api/db 三源编辑器、批量编辑、审核 UI | 移除相关页面/路由 |
| 抽取配置（Schema/类别/Prompt/脚本） | **删除** | 配方/覆盖模板用配置 | 移除页面；配方先配置文件 |
| RAG 问答/知识图谱/向量搜索 | **删除** | 不属于标准拆分 | 移除页面、接口、依赖 |
| API Key | **保留** | 外部对接需要 | 迁移 + 审计 |
| 邀请/成员 | **保留** | 知识库协作需要 | 迁移 + 审计 |
| 帮助/关于 | **保留/后置** | 不影响主流程 | 保留 |

结论：**术语集不作为独立功能保留**；保留“业务词典/别名管理”作为业务主数据的缓存与确认入口。
**前端先出“保留/改造/删除”清单，作为后端完善的输入。**

### 3.2 后端模块处置

| 模块 | 处置 | 说明 | 审计/改造要点 |
|---|---|---|---|
| parsekit（render/layout/ocr/assemble/rebuild） | **迁移 + 审计** | 流程可复用，代码需审计 | 页面/块并发、失败语义、文本层双源、产物契约 |
| 文档/任务/Outbox/arq/死信/心跳 | **迁移 + 审计** | 状态机与可靠性可复用 | 幂等、重试、超时回收、事务边界 |
| MinIO 存储/预签名/生命周期 | **迁移 + 审计** | 对象键/清理可复用 | 越权、路径注入、生命周期 |
| RBAC/RLS/审计 | **迁移 + 审计** | 知识库隔离保留，不简化 | 越权、RLS 绕过、审计完整性 |
| 知识库/工作空间/群组 | **迁移 + 审计** | 业务确认不简化，后续完善 | 成员/群组授权、邀请、RLS |
| API Key | **迁移 + 审计** | 外部对接需要 | 哈希、作用域、撤销、审计 |
| 术语集/术语条目 | **改造后迁移** | 改为业务词典/别名 | 同步语义、pending→active、误合并 |
| Prompt 模板/占位符 | **改造后迁移** | 业务白名单注入 | 只作辅助，不作主逻辑 |
| 结构化抽取 V3（41 类检索式） | **不迁移** | 不符合标准拆分 | 不进入当前项目 |
| `table_to_rows` | **不迁移** | 不展开 rowspan/colspan | 不进入当前项目 |
| chunker/retrieval/BM25/向量检索 | **不迁移** | 本期不做 RAG | 不进入当前项目 |
| `integration` 一站式 API | **重写/改造** | 引擎任务入口 | 认证、幂等、限流、错误码 |
| LLM 客户端 | **迁移 + 审计** | OpenAI 兼容 | 超时、重试、JSON、并发 |
| 前端代码 | **按 3.1 处置** | 保留/改造/删除 | 迁移部分必须审计 |

**审计原则**

- 审计对象是**确定要迁移/复用的代码**，不是全部旧代码；
- 先审计、后迁移；未审计的代码不得进入当前项目；
- 审计发现 bug 必须修复并补测试，不能带病迁移；
- 迁移/改造代码必须通过单元/契约/集成测试，不满足不合并；
- 不迁移模块直接删除，不留死代码/兼容分支。
- 输出 `docs/hansonDoc_RAG-audit.md`：模块清单、迁移/改造/删除、已知 bug、安全/依赖/数据隔离问题；
- 静态检查：ruff/mypy/bandit（或等价）；
- 依赖审计：漏洞、许可证、版本锁定；
- 安全审计：认证、越权、注入、文件上传、RLS/租户隔离、密钥；
- 结论：高风险项为 0 才允许迁移。

**已知问题审计清单（不得原样带入）**

- `integration` 端点无认证、superuser 绕过 RLS；
- `return_type=object` 未实现，标准信息返回错误数组；
- `table_to_rows` 不做 rowspan/colspan 合并；
- 大表被 chunk 切碎，检索窗口决定完整性；
- 41 类固定类别 + 检索式抽取，无法证明覆盖；
- `match_record` 语义优先 + 阈值硬编码，存在误合并风险；
- 术语集同步“清空重导”，会丢人工审核状态；
- 抽取失败不重试/状态回写不一致等任务边界问题（审计时逐项确认）。

## 5. 新增/调整里程碑详述

### 5.1 M1.6 表型配方 + 列绑定

**目标**：把“格式差异”从代码转移到声明式配方；把“这一列是什么”变成可审计的列绑定。

**范围**
- 配方 schema：结构签名、列绑定、别名/单位、修复规则、覆盖模板、业务词典绑定、版本/状态。
- 表型签名：profile、列数、表头 token、方向、块数、跨页特征。
