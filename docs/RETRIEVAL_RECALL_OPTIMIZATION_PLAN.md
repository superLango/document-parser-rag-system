## 1. 诊断方法

### 2.3 根因显微验证（化学成分 / 检测项目术语表）

- 术语集 283 条,`value_field=NAME`（均为元素符号 C/Si/Mn/Cr/Ni/Mo/Cu/N/P/S…）
- **精简输出 = `['Sr', 'V', 'Be', 'Cd']`** —— 术语表顺序前 4 个,而文档实际出现的 C/Si/Mn/Cr/Ni/Mo/Cu/N/P/S 全部被丢弃
- 机制：BGE-M3 对元素符号的余弦相似度实测 **0.55~0.77（C↔Si 0.55, C↔N 0.77）,均 < 0.85 去重阈值**,因此语义去重**几乎不触发送出**,`_build_refined_terms` 退化为"按术语表顺序截断前 limit 个"
- 用户关注点成立：**精简（语义去重）过滤掉的不是"近义重复",而是"术语表前几项",恰恰把文档中真实出现的术语全部排除在 query 外**
- 进一步:B_full(全量)与 E_gold(理想)基本持平(0.914 vs 0.916),说明"再多术语也不稀释到有害程度"——长 query 稀释不是当前主要瓶颈,丢术语才是

## 3. 市面方案调研（2026-08,摘要）

1. **候选取大 + 重排缩小**（主流最佳实践）：Qdrant/Weaviate/Elasticsearch 官方均建议混合检索先用大候选集（50~200）再 cross-encoder 精排到 top 10~20;本项目 `candidate_mult=2`、召回 top 8~10 明显偏小。[Qdrant Hybrid+rerank](https://qdrant.tech/documentation/tutorials-basics/reranking-hybrid-search/)、[Milvus 混合检索](https://markaicode.com/architecture/milvus-hybrid-retrieval-architecture/)、[RAG 检索召回率](https://blog.csdn.net/qq1137623160/article/details/160819432)
2. **RRF 融合局限**：RRF 只按排名不按分数,要求各路子结果质量有下限;[《An Analysis of Fusion Functions for Hybrid Retrieval》(arXiv 2210.11934)](https://browse.arxiv.org/abs/2210.11934) 给出 RRF/加权和/凸组合的对比;候选截断会直接放大 RRF 排名噪声(本项目证实)。
3. **query 构建**：
   - 术语表/词汇表驱动的检索普遍用 **query expansion + 文档感知选择**:先按文档频率/匹配度选术语再进 query（本项目 `_select_terms_by_doc_frequency` 思路正确,但只用于 rerank query,且其"核心词提取+子串去重"对元素符号有害——'C' 是 'Cr' 子串被去掉）
   - **多查询/子查询分解**:长 query 拆成多个子查询并发检索再融合,避免单向量平均化;[NVIDIA NIM RAG techniques(Query Rewriting/Multi-Query)](https://github.com/shaikn6/nvidia-nim-rag-techniques)、[query decomposition(HADES)](https://github.com/toddwbucy/HADES/commit/77a1f4ee34f89773fe758a8bf36fc0f79a72df05)
   - BGE-M3 官方 FAQ:query/passage 无需加前缀;[BGE-M3 discussion](https://huggingface.co/BAAI/bge-m3/discussions/35)
4. **表格类内容**（与本项目强相关）:
   - [TableRAG](https://blog.csdn.net/qq_54708219/article/details/156729218):表模式(schema)+ 单元格值双路检索,把"表头/列名/行描述"作为独立索引单元,比整表向量更精准
   - [表头感知的表格表示(STAR)](https://dl.acm.org/doi/pdf/10.1145/3774904.3792962):header-aware 聚类 + 自适应加权融合
   - [表格数据层级节点+表头表示 RAG](https://ieeexplore.ieee.org/document/11003975):在表头中编码层级信息
5. **稀疏/稠密融合权重**:RRF 一刀切方式可被加权凸组合替代;本项目 `keyword_weight=1.2 > dense_weight=1.0` 偏词法,对"符号 vs 中文名"失配场景不利。

## 4. 优化方案

### P0-1 术语精简逻辑改为「文档感知精选」（核心修复）

**现状**：`_build_refined_terms` 语义去重(Naive greedy)仅凭术语集内部相似度,丢术语;对元素符号余弦 0.55~0.77 时 gready 不触发,退化为顺序截断。

**改法 A（推荐,改动小）**：把"精简"换成"文档频率精选"（复用 `_select_terms_by_doc_frequency`,它本来就在 rerank query 里）：query 术语 = 当前文档中实际出现的术语（子串/词元命中）按频率 TopN,同时**禁止子串去重删除短符号**（'C' ∈ 'Cr' 不删）。数据流：`_build_query_terms` 增加 per-document 分支。

**改法 B（保守）**：`dedupe=True` 时仍做语义去重,但把初选顺序改为"文档频率降序",再取前 limit 个;至少保证保留的是文档高频词。

**改法 C（兜底）**：对纯符号类 value_field（正则 `^[A-Za-z0-9]{1,3}$`）直接跳过精简,用全量（实测 B_full ≈ E_gold,30 项不稀释）。

预期：化学成分 A 0.759 → ≥0.95（对齐 B_full）,室温拉伸 0.899 → 0.95。

### P0-2 候选集扩大（retrieval 预算重构）

- `category_recall.top_k`: 8 → **25**;`per_dim_top_k`: 10 → **30**
- `data_route_top_k`: 10 → **25**;`meta_route_top_k`: 5 → **15**
- `candidate_mult`: 2 → **4**（稠密路每维取 top_k*4 再融合;文档块数 20~65,总候选可控）
- `context_top_k`: 30 → **40**
- 前端 GlobalConfig 同步修改 schema 默认与页面提示。

预期:热处理制度类 Recall 0.50 → 0.75+;化学成分类多表场景 0.86 → 0.95+。

### P1-1 重排器启用并修正阈值语义

- 5/6 KB 的 `reranker.enabled=false` 且 `threshold=0.0`（默认）——直通时 rerank_score=None,`category_builder.py:472-481` 的类别级过滤 `max_rerank is None or max_rerank < threshold` 会误判 `None < 0` 为真?**不**:`None < 0` 实际为 `True` 若按 Python 比较会 TypeError——请核对:代码写 `if max_rerank is None or max_rerank < rerank_threshold:` 对 None 短路为 True → **整个类别被跳过**。即当前 5 个 KB 的"非 always"类别会被误剔除!这是比"候选缺失"更严重的 bug。
  - **建议**：直通重排时跳过类别级过滤（`if reranker.get("enabled")` 为 False 或 model 为空 → 不执行过滤）;或把默认 `category_filter_enabled` 在直通时置 False。
- `threshold=0.0` 语义为"保留正分":CrossEncoder logits 常为负分（不相关）,0.0 会把"弱相关但正确"的块全滤掉,应默认 `threshold=-2.0` 或 0.0 但配合 block_filter_enabled=False。

### P1-2 query 构建优化（降噪 + 基线化）

- 数据路 query 去掉 `fixed_query` 污染以外的"20+ 术语平铺",改为:**类型名 + 文档频率精选术语(≤10) + 字段名(≤5)**（即把 rerank query 修好后用于检索,方案 C 修复后重测）
- 增加**子查询并行**（方案 D 可选项）：化学成分类 query 拆 2~3 个子 query（如按"元素符号组/牌号/方法代码"分组）,`retrieval_service.search` 各自跑,再合并去重;实现对长 query 稀释的鲁棒性。
- BGE-M3 已确认无需 query 前缀。

### P2-1 表格增强完整性

- `_MAX_DESCRIBE_ROWS` 15 → **全表**（或数值列统计 + 行采样,上限按 100 行列）。
- 表头增强去重:"化学成分(质量分数)/%" × 11 的重复列名是 `table_cleaner` 列名识别问题（跨列表头默认展开重复),需在增强阶段合并重复表头列名后再生成概述（本次已观察到化学成分类的增强文本表头重复严重）。
- 大表(>40 行)建议:行级子块（TableRAG 思路）,即"表头+若干行"作为独立子向量,避免单块向量语义过载。

### P3（验证脚本固化）

- `qa/functional/retrieval_recall_diag.py` 已固化,支持选 KB/文档/类别;后续每次改动跑一遍,以 recall_diag.json 对比回归。
- 建议把 gold 术语判定（文档出现）与 Recall@k 纳入 `qa/evaluation/evaluate_phase6.py` 之外的独立检索门禁。

## 7. P0-1 落地与回归验证（2026-08-28 补充）

### 7.1 双路线原则

P0-1 在**新路线**实现,与现有路线并存、互不影响,供后续 A/B 对比:

- **V1(现状,不动)**:`backend/app/services/extraction/category_builder.py` —— 术语集内部语义去重精简
- **V2(新增)**:`backend/app/services/extraction/category_builder_v2.py` —— 文档感知术语精选
  - `build_one_v2()`:与 `build_one()` 同构,唯一差异是术语选择
  - 新函数:`_select_terms_by_doc_frequency_v2` / `_build_query_terms_v2` / `_build_data_query_v2`
  - 要点:符号术语用**词元匹配**(避免 'C' 误命中 'Cr');**不做子串去重**(V1 的 `w in k or k in w` 会顶掉 C/Cr);只保留「当前文档中实际出现」的术语;文档命中为空时回退 V1 语义去重(query 保证非空)
  - 数据路/元信息路/rerank 查询、类别召回、两路检索、过滤、schema 补全与 V1 完全一致(复用 category_builder 的 `_build_meta_query`/`_build_rerank_query`)

### 7.4 迭代：术语全保留（不限数量），仅文档感知精选（2026-08-28 续）

按评审意见将 V2 策略改为「**无论符号还是中文词组，query 术语不设数量上限**，

- `_select_terms_by_doc_frequency_v2` 的 `top_n` 改为可选（默认 None = 不截断）；

## 11. 84 个 recall=0 实例根因排查（2026-08-29）

### 11.1 结论

**84 个 recall=0 实例中,72 个(86%)是测试脚本 gold 判定假阳性(文档无该类别内容),
仅 12 个(14%)是真内容漏检(检索引擎/索引侧问题)。**

### 11.2 根因链条

1. **测试脚本 bug**:`retrieval_v3_full_test.py` 的 gold 判定逻辑:
   ```python
   if not gold_tbl:  # 字面匹配无目标块
       sem_ev = await category_builder_v2._semantic_evidence_hit(...)
       if sem_ev.get("hit"):
           gold_tbl = [sem_ev.get("chunk_id") or ""]  # ← _semantic_evidence_hit 修复前没有 chunk_id 字段 → None
   ```
   `_semantic_evidence_hit` 原返回 `{hit, max_sim, table}`,**无 chunk_id**,
   `sem_ev.get("chunk_id")` 返回 None → `gold_tbl=[None]` → 检索永远匹配不到
   → 人为 recall=0。已修复:函数返回 `chunk_id` 字段;
2. **语义证据阈值 0.65 偏严**:JBT7030(实测**确实有持久性能表**)
   的"高温光滑持久"语义 max_sim=0.6165(阈值 0.6 可通过),0.65 未命中;
3. **真实漏检 12 个**:语义证据(阈值 0.6)仍命中为真内容,但候选未覆盖目标块
   —— 属索引侧(表格增强文本行数/表头重复)或候选截断末梢。

### 11.3 定性验证(样本)

- JBT7030-2014 存在"持久性能"列表格 + `ASTM E 139/E 292` 持久方法;
  "高温光滑持久"语义 max_sim=0.6165(0.60 命中 / 0.65 未命中);
- 72 个假阳性实例:语义证据(0.6)判定无内容,即文档无该类数据
  (如 DFHM-QCD-0706-000885 锻件规范,文档"持久"出现 0 次)。

### 11.4 修复动作

1. **已修**:`_semantic_evidence_hit` 返回 `chunk_id`(生产代码缺陷,不只测试);
2. **gold 判定修正**:测试脚本如需语义兜底判定目标块,应使用真实 chunk_id,
   否则跳过该实例(而非标 None);
3. **阈值建议**:语义证据阈值降到 **0.60**(实测 JBT7030 真内容 0.6165、
   无内容类 0.55 以下,0.60 分界更准;0.65 会漏掉部分真内容);
4. 12 个真实漏检实例待 P2-1(表格增强行数/表头重复修复后重测)。

### 11.5 最终真实效果估计

修正后:`recall=0` 从 84 降到约 12(14%↓86%),真实总体 Recall ≈
V3 的 0.767 + 12 个真漏检 ≈ **0.79~0.80**;假阳性清零后,84 个实例中
72 个本应"无内容剔除"(不进统计),实际 Recall 计算更准确。

### 15.2 端到端（稳态）

| 阶段 | 耗时 |
|---|---|
| OCR 解析 | 16.7s |
| 入向量索引 | 2.5s |
| 类别召回/剔除（预热点后） | ~111s |
| **送入 LLM 前合计** | **~130s** |

### 15.3 优化空间

- 类别召回阶段 111s 是主耗时（41 类串行 × 2.7s）;
- pipeline 中类别抽取已用 `asyncio.gather` 并行, **build_one_v2 也可并行化**（并发 limit 由 LARGE_CANDIDATES/全局配置控制）→ 预期 111s → 30~40s（4 并发）;
- 语义证据判定（~3.8s/类, 仅字面0命中触发）可通过「类别 query 批量 embed + 向量矩阵一次 dot」优化。

## 16. 类别召回并行化与语义证据批量优化实验（2026-08-29）

### 16.1 环境核查

- GPU: GB10 单卡(共 4 进程: vLLM 38.8GB + 2×后端 Python + 其他);
- **Embedding 服务单线程 executor + asyncio.Lock**（防 GB10/torch 跨线程死锁设计，不可违反）;
- arq max_jobs=10; reranker 类级单例 to_thread。

### 16.2 方案 A: 语义证据批量（已落地, 有效）

- 新增 `_load_doc_block_vectors`（共享缓存 `_block_vec_cache`）+ `_batch_semantic_evidence`（一次 embed 全部 query + 矩阵 dot）;
- 1: `_semantic_evidence_hit` 改用共享矩阵（不再逐块循环）;
- 实测（41 类真实 query，平均 17 字符）: 批量 0.07s vs 逐类 0.38s, **5.6x**; 命中一致（11/11）;
- 注意: 用全量/超长 query 时批量反而慢（41×2000 字符 embed 需时），真实负载短 query 批量优势明显。

### 16.3 方案 B: 类别检索并行化（实测无效, 已改造保留）

- pipeline route=v3 改为 `asyncio.gather + Semaphore(route_concurrency 默认 8)`; `BaseException→Exception`;
- **实测: 串行 111.23s / 并行8 110.10s / 并行4 110.98s —— 加速比 1.0x**;
- 根因: GPU 是唯一瓶颈（embed 串行锁 + reranker 类级 to_thread 全部序列化），
  asyncio 并发仅重叠 DB ANN/BM25 IO（~0.001s/次, 可忽略）;
- 结论: **该环境（单 GPU + 单线程 embed + 类级 reranker）并行召回无收益**;
  pipeline 并行改造对多路 DB / 多 GPU / 远程批次场景有益，保留。

### 16.4 当前最优耗时（稳态, 41 类）

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 类别召回/剔除 | 111s（串行） | ~70s（语义证据批量 + 共享矩阵, 其余不变） |
| 端到端送 LLM 前 | ~130s | **~90s** |

### 16.5 进一步优化方向（如需）

- 若未来多 GPU 或独立 reranker 服务: 并行召回可复现加速;
- reranker 推理本身 ~0.5-1s/类×41=20-40s（类级缓存后首载除外）;
- 候选放大（LARGE_CANDIDATES top_k=40）比默认 top_k 大, 重排候选多;
  若可容忍略降召回, 减小 top_k 可显著降重排耗时。
