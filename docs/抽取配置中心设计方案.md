# 结构化抽取配置化（抽取配置中心）设计方案 v3

> 目标：将 v3 结构化抽取中硬编码的 Schema 定义、Prompt 模板、抽取规则、验证规则，以及**与材料行业专属三表（sm_feature/sm_item/sm_method）的耦合**，改造为**按知识库（KB）可配置**，实现零代码/低代码完成抽取策略定制与调整，并支持领域切换与版本管理。
>
> **v3 关键变更**（基于第二轮评审）：
> 1. **三表抽象为「数据集」**：将材料行业专属的三表，抽象为通用「数据集（Dataset）」概念，支持不同行业自定义表结构、数据源（接口/数据库/手动），并与 Schema 动态组装、与抽取阶段解耦。
> 2. **术语库页面双页签**：术语库页面同时承载「术语集」与「数据集」两类配置，数据集可通过接口调用或数据库连接方式完成配置。
> 3. **抽取阶段配置优化**：类别召回、五维 query 上下文、enum 绑定、归一化/白名单数据源全部改为「数据集驱动」，并增加数据集预加载缓存与按数据集降级。
> 4. **保留 v2 成果**：Schema 模块重构（`SchemaConfig` 双轨收敛）、抽取配置独立模块、工作流调研结论（不引入重型引擎）。

## 一、现状分析

### 1.1 抽取流水线（v3）

入口 [extraction_pipeline.py](../backend/app/services/extraction/extraction_pipeline.py) 串联三段：

```
Phase 2 类别构建        Phase 3+4 抽取           后处理
  category_builder        ├ doc_info(单次)        post_processor
  ├ 【三表】加载           ├ categories(并发)      ├ 项目名归一化
  ├ 五维query编码          └ heat_treatment       ├ 方法年代号
  ├ 并发hybrid_search      └ 每项：检索→组装→LLM   ├ 温度分类修正
  ├ 置信度过滤                                    ├ 跨类校验
  └ schema_builder 构建三类schema                 └ 去重
```

### 1.2 三表硬编码问题（本版核心痛点）

三表（`sm_feature`/`sm_item`/`sm_method`）是**材料行业的专属结构**：

| 表 | 角色 | 字段（硬编码） | 使用场景 |
|----|------|--------------|---------|
| `sm_feature` | 项目大类 | id/name/flag | 类别召回来源 |
| `sm_item` | 检测项目 | name/english_name/item_alias/unit/feature | item enum、归一化、白名单、五维 query |
| `sm_method` | 检测方法 | name/method_code/type/range/feature | method enum、五维 query |

**问题**：
1. **行业绑定**：三表结构（`feature`/`item`/`method` 语义）仅适用于材料检测。其他行业（医疗/合同/其他）可能有完全不同的表结构、不同的关系（如医疗的"部位/指标/器械类别"）。
2. **代码耦合**：`base_table_loader`/`base_data_store`/`item_matcher`/`category_builder` 全部硬编码 `SmFeature`/`SmItem`/`SmMethod` 模型，换行业必须改代码。
3. **数据源单一**：仅支持"从 PostgreSQL 同步"，不支持接口拉取或自定义数据库连接。

### 1.3 Schema 模块双轨问题

当前两套平行 Schema 体系（`SchemaConfig` 父子层级 vs v3 `schema_builder` 硬编码字段），v3 绕过 `SchemaConfig`。详见 v2 方案，本版保留其重构思路。

### 1.4 硬编码清单（全部可配置化）

| 阶段 | 模块 | 硬编码内容 | 迁移去向 |
|------|------|-----------|---------|
| 前 | `schema_builder.py` | `CATEGORY_FIELDS`/`HEAT_TREATMENT_FIELDS`/doc_info | `SchemaConfig`（重构） |
| 前 | `prompts/*.yaml` / `field_descriptions.yaml` | 模板/字段描述 | 抽取配置（新表） |
| 前 | `extraction_config.py` | 全局 `EXTRACTION_V3_*` | 抽取配置 |
| 前 | `base_table_loader`/`category_builder` | **三表硬编码** | **数据集（Dataset）** |
| 中 | `hybrid_searcher.py`/`context_assembler.py` | 检索权重/上下文规则 | 抽取配置 |
| 中 | `glmocr_extractor.py` | 分批/截断/重叠 | 抽取配置 |
| 后 | `post_processor.py`/`cross_validator.py`/`item_matcher` | 温度/归一化/跨类/去重 | 抽取配置 + 数据集 |

## 二、配置数据承载分层（收敛数据集边界）

### 2.1 原则：不是所有列表都建数据集

数据**体量、动态性、来源**决定承载方式，避免过度设计。配置数据分四类承载：

| 数据形态 | 特征 | 承载方式 | 建数据集？ |
|---------|------|---------|-----------|
| 静态枚举（单位/方向/位置/温度类型） | 小、静态、语义固定 | Schema 静态 enum（`enum_source=static`） | **否** |
| 术语/别名 | 语义词典、中等体量 | 术语库（term_base） | **否** |
| 类别列表（feature） | 中等、较稳定、领域结构 | 轻量类别配置（`kb_categories`） | **否**（默认） |
| 大参考数据（item/method/检测项目） | 大、动态、来自外部系统 | 数据集（API/DB 拉取 + 向量化 + 归一化） | **是** |

### 2.2 数据集适用边界（何时才建数据集）

**数据集仅用于"大而动态、来自外部系统的参考数据"**，需同时满足：
- **体量大**（数百~上万条），不适合手工配置
- **动态变化**（由外部系统维护），需定期拉取
- **有结构化字段**（group/value/alias/unit），需参与向量化、归一化、白名单

典型场景：材料检测的 item/method 目录、医疗的器械/指标目录。除此之外，**小枚举用 Schema enum、语义词典用术语库、类别列表用轻量配置**，一律不建数据集。

### 2.3 数据集定义（收敛后的 role）

`role` 收敛为两类核心：

| role | 用途 | 例如 |
|------|------|------|
| `item` | 大参考数据：enum + 归一化 + 白名单 + 五维 query | 检测项目、器械指标 |
| `method` | 方法库：enum + 五维 query | 检测方法、试验标准 |

> 类别列表（feature）默认用轻量配置即可（见 2.1），**不强制建数据集**；仅当类别需从外部大量拉取时，才可选建 `role=feature` 数据集。已移除 v3 中 `enum`/`normalize`/`custom` 等过度角色（静态枚举走 Schema enum、归一化复用 item 数据集、扩展逻辑走 Hook）。

数据集定义：

| 属性 | 类型 | 说明 |
|------|------|------|
| id / kb_id | UUID | 属干 KB（RLS 隔离） |
| name / code | String | 名称 / 唯一编码 |
| role | String(20) | `item` / `method`（及可选 `feature`） |
| source_type | String(20) | `manual` / `api` / `db` |
| source_config | JSON | 数据源配置（见 2.4） |
| group_field / value_field / alias_field / unit_field | String | 字段映射 |
| field_defs | JSON | 字段定义 |
| cache_policy | JSON | TTL / 预加载 |
| is_active | Boolean | |

### 2.4 数据源类型

| 类型 | source_config 示例 | 说明 |
|------|-------------------|------|
| `manual` | `{ rows: [...] }` | 页面手动录入，落 `kb_dataset_entries` |
| `api` | `{ url, method, headers, auth, response_path, mapping }` | 通过接口拉取，mapping 将接口字段映射到数据集字段 |
| `db` | `{ dsn, driver, table, query, mapping }` | 直连外部数据库，query 拉取，mapping 映射字段 |

> `mapping` 是关键：声明"接口/数据库列 → 数据集字段（group/value/alias/unit）"的映射，使**任意表结构**都能接入，正是解决"其他行业表结构不同"的核心。

### 2.5 Schema 构建设计（模板 → 类别 → 字段，三层）

**Schema 构建采用三层结构**（与现有 `SchemaConfig` 父子层级衔接，字段提升为可配置实体）：

```
Schema 模板（template）
 └─ 类别（category，父级）
     ├─ return_type: object | array          ← 类别返回类型
     ├─ is_active: 是否参与抽取              ← 类别总开关
     ├─ extraction_strategy: auto|always|never ← 参与 Phase 2 置信度过滤的策略
     ├─ query_mode: dataset|fixed            ← 五维 query 构造方式
     ├─ datasets: 绑定数据集列表（item/method）← 类别级数据源绑定（含 Phase 2 query 语义）
     └─ 字段（field，子级）
         ├─ 字段名 / 类型 / 说明 / 示例      ← 不绑定数据源，仅用于提升抽取精度
```

**类别级绑定**（决定该类别的枚举/上下文来源 + Phase 2 query 语义）：

```json
{
  "name": "拉伸性能",
  "return_type": "array",        // object | array
  "is_active": true,             // 类别总开关
  "extraction_strategy": "auto", // auto:按置信度过滤 | always:强制抽取 | never:从不抽取
  "query_mode": "dataset",       // dataset:用绑定数据集构造 query | fixed:用固定文本
  "fixed_query": "",             // query_mode=fixed 时使用
  "confidence_threshold": 0.35,  // 可选，覆盖全局默认阈值
  "top_k": 5,                    // 可选，覆盖全局检索 top_k（如 doc_info/heat_treatment 类别专用）
  "prompt_template_id": "uuid",  // 可选，绑定 Prompt 模板
  "datasets": [                  // 支持多数据集（item 与 method 分开，供 Phase 2 query 使用）
    {"dataset_id": "item数据集", "role": "item",   "group_field": "feature", "value_field": "name"},
    {"dataset_id": "method数据集", "role": "method", "group_field": "feature", "value_field": "stds"}
  ],
  "fields": [
    {
      "name": "项目名称",
      "type": "string",
      "description": "从数据集中匹配...",
      "example": "C",
      "required": true
    }
  ]
}
```

**字段不绑定数据源**：字段仅通过 `type`（类型）、`description`（说明）、`example`（示例）提升模型抽取精度，不绑定数据源列。数据源绑定仅发生在类别级（`datasets`）。

**类别节点默认值与联动（前端交互）**：

| 字段 | 默认值 | 联动规则 |
|------|-------|---------|
| `is_active` | `true`（抽取） | 总开关，关闭则该类别不参与 Phase 2 |
| `extraction_strategy` | `auto` | 仅当选择 `auto` 时，才显示并可配置 `confidence_threshold`（及无召回/低置信度剔除规则）；`always`/`never` 不显示阈值配置 |
| `query_mode` | `fixed` | 默认 `fixed` 时显示 `fixed_query` 文本输入框；选择 `dataset` 时，文本输入框切换为**数据集选择器**（绑定 `datasets` 中 `role=item/method` 数据集） |
| `confidence_threshold` | 0.35 | 由 `extraction_strategy=auto` 触发显示 |
| `datasets` | 空 | 由 `query_mode=dataset` 触发显示 |

**组装流程**：
```
Schema 模板 → 遍历类别 → 按 return_type 决定对象/数组 → 类别绑定的数据集按 group_field 过滤 → 
字段绑定的数据源列取枚举 → 递归组装为有层次的 Schema → 供 prompt 构建 / 模型抽取
```

**字段说明与示例**：字段 `description` + `example`（复用现有 `sample_fields` 能力），保证抽取精度。

### 2.6 Schema 模板参与 Phase 2（类别召回 / query / 置信度过滤）

**核心变化**：类别集合来源从三表（`sm_feature`）改为 **Schema 模板的类别节点**。模板类别即抽取目标，`sm_feature` 的角色由模板类别承担，`sm_item`/`sm_method` 由类别绑定的数据集承担。

**改造后 Phase 2 流程**：

```
输入：激活的 Schema 模板 + 文档五维向量
 1. 类别列举：遍历模板，取 node_type=category 且 is_active 的节点 → 候选类别列表
 2. 语义加载：每类别从绑定数据集拉取条目（按 group_field 过滤，value_field 取值）
 3. query 构造：query_embedder 用类别条目 + 类别名构造五维 query
 4. hybrid_search：five_dim_vector_store.hybrid_search，top_k=5
 5. 置信度过滤与剔除（按 extraction_strategy）：
    - always → 强制保留，跳过过滤
    - never  → 剔除（不参与抽取）
    - auto   → 无召回剔除；max(score) < confidence_threshold 剔除
 6. schema 组装：保留类别 → 从模板组装三层 schema（return_type + 字段）
 7. 产出：targets（保留类别）/ skipped（剔除类别，含原因）→ 供 Phase 3+4
```

**query 构造（query_mode）**：
- `dataset`：类别 `datasets` 中 `role=item/method` 数据集 → 按 `group_field` 过滤当前类别 → 取 `value_field` 前缀 → 构造类别 query（替代原 `_load_items_and_methods` 读三表）。
- `fixed`：用 `fixed_query` 固定文本（如 doc_info 类别的 `"标准名称 标准编号 文件编号"`、heat_treatment 类别的固定关键词），不依赖数据集。

**hybrid_search**：仍为五维向量检索，目标 `doc_five_dim`，`top_k=5`（`_PHASE2_TOP_K`）。query 向量来源由三表条目改为类别数据集条目。

**置信度过滤与剔除的语义差异**：
| 维度 | 原实现（三表） | 改造后（Schema 模板） |
|------|--------------|---------------------|
| 候选来源 | `load_all_features()` 全量三表 | 模板 `is_active` 类别节点 |
| 过滤目的 | 判断 feature 是否存在于文档 | 判断该类别是否值得抽取 |
| 剔除冗余 | 无召回 / 低置信度 | 无召回 / 低置信度 / `never` |
| 用户显式保护 | 无 | `always` 强制抽取（用户要的类别不因召回低被误剔除） |

**降级策略**：类别无绑定数据集或数据集为空 → 类别 `query_mode` 自动降级为 `fixed`（用类别名 + 字段 example 构造 query），不阻断 Phase 2。

### 2.7 数据集预加载与降级

- **预加载缓存**：数据集按 `cache_policy`（TTL/预加载）缓存到内存/向量库，避免每次抽取重复调用 API/DB。
- **降级策略**：未配置 item 数据集时，跳过归一化/白名单，保留 LLM 原值；未配置 method 数据集时，仅不注入方法枚举。

## 三、工作流调研结论

**不引入重型工作流引擎**（Temporal/Prefect/Airflow）。理由：产品定位为「知识库配置中心，流程骨架固定、用户填参数」（项目记忆），当前 arq 轻量异步队列已满足固定线性流水线（Phase 2→3→4）编排；引擎解决的是「流程拓扑可重排」，与「固定流程内字段/规则可调」粒度错配，且引入运维负担与确定性约束（与 LLM 非确定性冲突）。

采用**「固定骨架 + 阶段级配置 + Hook 特殊节点」**；未来若需自定义流程拓扑，再评估轻量 DAG（配置表 + 自研执行器）。

## 四、目标架构

```
v3 流水线（执行引擎）
  │  注入 kb_id
  ▼
ExtractionConfigResolver（独立模块）
  ├─ 引擎/参数      ← kb_extraction_config
  ├─ Prompt 模板    ← kb_prompt_templates
  ├─ 后处理规则     ← kb_extraction_rules
```

## 五、数据模型设计

### 5.1 数据集模块（新增，替代三表硬编码）

**① `kb_datasets`（数据集元数据）**

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| kb_id | UUID FK | |
| name / code | String | 名称 / 唯一编码 |
| role | String(20) | `item`/`method`（可选 `feature`） |
| source_type | String(20) | `manual`/`api`/`db` |
| source_config | JSON | 数据源配置（url/dsn/query/mapping） |
| group_field / value_field / alias_field / unit_field | String | 字段映射 |
| field_defs | JSON | 字段定义 |
| column_aliases | JSON | 列别名映射 `{原列名: 别称}`（同步用原列名，展示/抽取用别称） |
| cache_policy | JSON | TTL/预加载 |
| is_active | Boolean | |

**② `kb_dataset_entries`（数据集条目，仅 manual 或缓存落库）**

| 列 | 类型 | 说明 |
|----|------|------|
| id | UUID PK | |
| dataset_id | UUID FK | |
| kb_id | UUID FK | |
| group_key | String | 分组值（类比 feature） |
| value | String | 值（类比 name） |
| aliases | JSON | 别名数组 |
| unit | String | 单位 |
| extra | JSON | 扩展字段 |

> 材料三表迁移：`sm_feature`→轻量类别配置（`kb_categories`，不建数据集）；`sm_item`→`kb_datasets(role=item, group_field=feature, value_field=name, alias_field=item_alias, unit_field=unit)`；`sm_method`→`kb_datasets(role=method, group_field=feature, value_field=method_code)`。条目迁移到 `kb_dataset_entries`。

### 5.2 Schema 模块重构（`schema_configs` + 模板）

**三层结构**：`SchemaTemplate`（模板）→ `SchemaConfig`（类别，父级）→ 字段（子级，进化为可配置实体）。

- **`schema_templates`（新增）**：模板容器。列：`id`/`kb_id`/`name`/`description`/`is_active`。
- **`schema_configs`（扩展）**：表示类别（父级）。`parent_id` 指向模板；新增 `node_type`（`category`/`field`）、`return_type`（`object`/`array`）、`dataset_id`/`group_field`/`value_field`（类别级数据集绑定，唯一数据源绑定点）。
- **字段**：作为类别下子节点（`parent_id` 指向类别），仅含 `type`（类型）/`description`（说明）/`example`（示例）/`required`，**不绑定数据源**，用于提升抽取精度。

现有 `sample_fields` 保留（字段示例），`/schemas/{parent_id}/merged` 端点升级为分层组装（见 2.5）。

### 5.3 抽取配置中心（保留 v2 六表）

`kb_extraction_config`/`kb_prompt_templates`/`kb_extraction_rules`/`kb_validation_rules`/`kb_term_binding`/`kb_domain_config_versions`（详见 v2 设计，不重复）。

**配置分层（三层，覆盖 Phase 2/3/4）**：

| 层 | 载体 | 内容 | 作用域 |
|----|------|------|--------|
| 全局层 | `kb_extraction_config` | Phase 2/3/4 通用参数（检索/LLM/并发/批处理/后处理开关） | KB 级，一处生效 |
| 类别层 | Schema 模板类别节点 | query_mode / fixed_query / datasets / extraction_strategy / 阈值 / Prompt 绑定 / top_k 覆盖 | 单类别 |
| 模板层 | `kb_prompt_templates` | system/user/字段定义文本 | 可复用，类别绑定 |

**全局配置区块（`kb_extraction_config.content` JSON）**：

```json
{
```

## 六、术语库页面改造（双页签）

术语库页面由单一「术语集」扩展为**双页签**：

| 页签 | 内容 | 数据来源 | 操作 |
|------|------|---------|------|
| **术语集** | 术语/术语集/术语映射（现有） | term_bases / terms / term_mappings | 既有能力保留 |
| **数据集** | 数据集定义 + 数据条目 + 数据源配置 | kb_datasets / kb_dataset_entries | 新增 |

**数据集页签功能**：
1. **数据集列表**：展示 KB 内所有数据集（名称/角色/类型/状态）。
2. **新建数据集**：选择 `source_type`（manual/api/db）。
3. **数据源配置**：
   - `api`：填写接口 URL/方法/凭证，可「测试连接」并「拉取预览」。
   - `db`：填写 DSN/驱动/表/查询（SQL 或整表），可「测试连接」并「查询预览」。
   - `manual`：页面表格录入条目。
   - **列自动生成**：数据集列以接口返回/查询结果/SQL 结果集的**表头实际创建**，无需手工定义列结构。
4. **列别名配置**：进入数据集后，用户可为表头添加**别称**（`column_aliases` = `{原列名: 别称}`）。**保留原列名**，同步/拉取仍用原列名，展示/抽取用别称，避免接口表结构变化导致不一致。
5. **角色配置**：声明数据集在抽取中的角色（`item`/`method`，可选 `feature`）。
6. **字段映射**：声明 value/group/alias/unit 对应列（基于列别名，适配任意表结构）。
7. **类别列表**：类别用轻量配置（`kb_categories`），不进数据集页签；仅当类别需从外部大量拉取时可建 `role=feature` 数据集。

## 七、后端改造设计

### 7.1 抽取阶段配置优化（数据集驱动）

| 阶段 | 原实现（硬编码三表） | 优化后 | 数据承载 |
|------|---------------------|--------|---------|
| 类别召回 | `base_table_loader.load_all_features()` 读 sm_feature | 读 **Schema 模板 `is_active` 类别节点**（替代 kb_categories） | Schema 模板 |
| 五维 query 上下文 | 读 sm_item/sm_method | 读类别绑定 `role=item/method` 数据集，按 group 过滤 | 数据集 |
| 置信度过滤 | 按 feature 过滤 | 按类别 `extraction_strategy`（auto/always/never）+ 阈值 | Schema 模板 |
| enum 绑定 | 固定 items/methods | Schema 字段 `enum_source` 动态绑定（小枚举用 `static`，大表用 `dataset`） | Schema + 数据集 |
| 归一化 | `item_matcher` 读 sm_item | 读 `role=item` 数据集 | 数据集 |
| 跨类白名单 | 读 sm_item.feature | 读 item 数据集 group_field | 数据集 |
| 数据源 | PostgreSQL 同步 | 仅大数据集用 manual/api/db 三态 + 缓存 | 数据集 |

### 7.3 流水线改造

- `category_builder`：类别来源改为 **Schema 模板类别节点**（`is_active`），query 语义改为读类别绑定数据集（`DatasetService`），置信度过滤按 `extraction_strategy`（详见 2.6）。
- `schema_builder`：改为从 Schema 模板组装（模板→类别→字段），不再硬编码 `CATEGORY_FIELDS`；`enum_source=dataset` 时绑定数据集。
- `prompt_manager`：优先读 `kb_prompt_templates`，缺失回退内置 YAML。
- `post_processor`/`cross_validator`/`item_matcher`：数据源改为数据集，规则按 `kb_extraction_rules` 开关。

## 十二、风险与注意事项

1. **数据集通用性**：mapping 与 role 设计必须足够通用，避免把材料行业语义（feature/item/method）写死为默认。
2. **数据源安全**：API 凭证、DB DSN 需加密存储；DB 连接最小权限；接口拉取加超时与限流。
3. **缓存一致性**：数据集变更需失效缓存；API/DB 数据源需 TTL 与手动刷新。
4. **Schema 双轨收敛**：重构后 v3 必须消费 `SchemaConfig`，旧 LangExtract 线路兼容新结构。
5. **模块职责分离**：抽取配置中心与配置中心、数据集模块各自独立，避免交叉引用。
6. **RLS 隔离**：所有新表带 `kb_id`，Resolver/DatasetService 显式过滤（纵深防御）。
7. **通用规则默认关闭**：温度/归一化/跨类等非通用规则默认关闭，仅材料检测开启。
8. **版本快照体积**：全量 JSON 压缩存储 + 限制保留数量。

> 工作流演进：若未来出现「用户自定义流程拓扑」需求，再评估轻量 DAG（配置表 + 自研执行器），本期不引入重型引擎。
