# 后处理与校验规则化设计（抽取配置中心 v3.1）

> **目标**：将 v3 抽取中**硬编码在 `post_processor.py` / `cross_validator.py` 的后处理与校验逻辑**，改造为与 **Schema 模板 / Prompt 模板** 同级的**通用可配置规则**，实现按知识库（KB）、按类别、按字段多级定制与开关，并支持领域切换与版本回滚。
>
> **本版关键决策**（三项，经确认）：
> 1. **统一为一张规则表**：废弃「抽取规则 `kb_extraction_rules` / 验证规则 `kb_validation_rules`」两张表的分离，合并为一张 `kb_rules`，用 `stage` 区分后处理 / 校验。
> 2. **支持类别 / 字段级作用域绑定**：规则可绑定到全局、特定类别、特定字段，形成覆盖链。
> 3. **仅交付设计**：本文档为设计产出，不包含实现代码。

---

## 一、背景与现状

### 1.1 现状：后处理与校验仍硬编码

`extraction_pipeline` 的 Phase 4 结束后，固定调用 `post_processor.process()` 执行 5 步，其中第 4 步委托 `cross_validator`：

| 步骤 | 实现 | 说明 | 现状参数（硬编码默认） |
|---|---|---|---|
| 归一化 | `_normalize_item_names_batch` | 项目名向量匹配优先，失败回落轻量匹配 | `item_matcher` 编辑距离阈值 0.85 |
| 方法年代号 | `_normalize_method_year` | 无年代号时补全最新方法 | 无 |
| 温度分类修正 | `_filter_by_temperature` | 高温/低温拉伸剔除不匹配，室温补室温 | 无 |
| **跨类校验** | `cross_validator.validate` | 项目名全表检索 + 白名单兜底 | `cross_validate_threshold` 0.35、白名单相似度 0.90 |
| 去重 | `_dedup` | 字段排序哈希去重 | `dedup_sim_threshold` 0.95 |

**问题**：
1. 逻辑与阈值**埋在代码里**，用户无法按 KB / 类别 / 字段调整。
2. 全局 `post_process` 开关（`defaults.py`）**存了但未接入** `post_processor.process()`（其无条件执行全部 5 步）。
3. 现有 `kb_extraction_rules` / `kb_validation_rules` 两张表**是空壳**：无种子规则、无执行引擎。

### 1.2 与已集成体系的对齐目标

Schema 模板 / Prompt 模板已具备的成熟机制，规则化后应同样具备：

| 机制 | Schema/Prompt 现状 | 规则化目标 |
|---|---|---|
| 载体 | 模板表 + 页面编辑 | 规则表 + 页面编辑 |
| 按 KB 隔离 | ✓ | ✓ |
| 可配置参数 | 字段/类别级配置 | 规则参数 schema |
| 三级回退 | 类别模板 → KB 模板 → 内置默认 | 类别/字段绑定 → KB 规则 → 内置规则 |
| 默认可用 | 内置模板 | 内置规则注册表 |

## 二、规则元模型（统一规则表）

### 2.1 设计决策

- **统一为一张表 `kb_rules`**，用 `stage ∈ {post, validation}` 区分后处理与校验，一套规则引擎共用，避免两套重复代码。
- **作用域链**：规则默认全局生效，可绑定到类别、可下沉到字段，三层覆盖（见第五章）。
- **内置规则注册表**：规则实现与参数 schema 由代码注册（类似「内置模板」），用户只做选择与参数，不写代码；特殊逻辑仍走 Hook。

### 2.2 表结构（`kb_rules`）

字段基于现有 `kb_extraction_rules` 扩展，**合并** `kb_validation_rules`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid pk | 规则实例 ID |
| `kb_id` | uuid fk | 知识库隔离（RLS） |
| `stage` | enum | `post`（后处理）/ `validation`（校验） |
| `rule_key` | string | 内置规则标识（见第三章注册表） |
| `name` | string | 显示名（允许自定义，默认取内置名） |
| `description` | string | 说明 |
| `enabled` | bool | 是否启用 |
| `sort_order` | int | 同 stage 内执行顺序 |
| `scope` | json | 作用域绑定：`{type: global|category|field, category_id?, field_id?}` |
| `params` | json | 规则参数（键值，由参数 schema 约束，见第三章） |
| `created_at` / `updated_at` | datetime | 审计 |

> **迁移**：新增 `kb_rules` 表；`kb_extraction_rules` / `kb_validation_rules` 数据迁移入 `kb_rules`（`stage=post` / `stage=validation`）后废弃两表。

## 三、内置规则注册表

规则实现 + 默认参数 + **参数 schema（供前端动态渲染表单）** 由代码注册，构成 `RULE_REGISTRY`。

### 3.1 后处理规则（`stage=post`）

| rule_key | 名称 | 默认参数（schema 驱动） | 现有实现映射 |
|---|---|---|---|
| `normalize_item` | 项目名归一化 | `match_sim_threshold: 0.85`、`use_vector: true`、`fallback_matcher: true` | `_normalize_item_names_batch` + `item_matcher` |
| `normalize_method_year` | 方法年代号补全 | `latest_only: true` | `_normalize_method_year` |
| `temperature_filter` | 温度分类修正 | `apply_categories: ["高温拉伸","低温拉伸","室温拉伸"]` | `_filter_by_temperature` |
| `dedup` | 记录去重 | `sim_threshold: 0.95`、`exclude_fields: ["_endkey"]` | `_dedup` |

### 3.2 校验规则（`stage=validation`）

| rule_key | 名称 | 默认参数 | 现有实现映射 |
|---|---|---|---|
| `cross_validate` | 跨类校验 | `sim_threshold: 0.35`、`whitelist_sim: 0.90`、`fallback_whitelist: true` | `cross_validator.validate` |

**新增通用校验规则**（跨类之外的常用校验，作为规则库能力）：
| rule_key | 名称 | 默认参数（示意） |
|---|---|---|
| `field_required` | 必填校验 | `fields: [...], policy: reject\|warn` |
| `field_enum` | 枚举校验 | `field, whitelist_source: term_base\|static, values: [...]` |
| `field_value_range` | 数值范围校验 | `field, min, max` |
| `field_consistency` | 字段一致性 | `field_a, field_b, operator: eq\|contains` |

> 新增规则沿用「注册表 + 参数 schema」模式，**无需改数据库结构**，仅注册实现与 schema 即可扩展。

### 3.3 参数 schema 约定

每个规则定义 `params_schema`（JSON Schema 子集），前端据此动态渲染参数表单（数字/枚举/开关/字段选择器），类似 Schema 类别配置的字段表单。合法值、默认值、提示语全部由注册表给出。

## 四、执行管道设计

改造 `post_processor.process()` 为**规则管道** `rule_engine.run()`：

```
输入：(schema 目标, 抽取结果 records, resolved_rules)
按 stage 分组 → 按 sort_order 排序 → 逐个执行 enabled 规则
每个规则：run(records, target, rule_params) → {kept, rejected, mutated}
```

- **规则接口**：`run(records, target, params) -> RuleResult`，输入输出结构化，可独立测试。
- **顺序**：`post` 阶段顺序 = 归一化 → 方法年代号 → 温度修正 → 跨类校验 → 去重（保持现有行为）；`validation` 阶段在校验后统一标记 `unverified / reject_reason`（仅测试面板可见，不泄漏到最终结果）。
- **兼容性**：内置 4 项后处理 + 1 项校验**默认全部启用**，参数取现有默认值 → 行为与现状完全一致，不破坏旧结果。

## 五、作用域绑定与三级回退

对齐 Prompt 模板的三级回退，规则解析按优先级取最终生效值与开关：

```
类别/字段绑定规则（最具体）  →  KB 级规则（全局）  →  内置默认规则
```

- **全局规则**：`scope={type:global}`，作用于所有类别。
- **类别级绑定**：`scope={type:category, category_id}`，覆盖全局同名规则；如 `temperature_filter` 仅对"高温拉伸"类别启用、其他类别关闭。
- **字段级绑定**：`scope={type:field, field_id}`，针对某字段的校验（如 `field_required` 只校验"取样数量"）。
- **解析时机**：`rule_engine` 在 `schema_builder` 组装出目标类别后，按 `kb_id + category_id + field_id` 解析出该类别生效的规则集与参数，再执行。

## 六、基于术语集的动态加载方案（核心）

规则与 Schema 一样，**不在启动时写死，而是在流水线运行时按 KB / 类别 / 字段动态解析**，且规则引用的**术语集数据按需加载**。整个链路对齐 Schema 模板的加载方式。

### 6.1 加载链路（对齐 Schema）

```
静态注册          DB 动态加载        作用域解析          术语集数据（按需）
规则注册表 ──►  resolver._load_rules ──► rule_engine.resolve ──► TermBaseValueLoader
(实现/参数schema)  (kb_rules 实例)      (字段>类别>全局>内置)   (按 term_base_id 加载+缓存)
```

| Schema 模板 | 后处理/校验规则 |
|---|---|
| `resolver._load_schemas()` 加载模板+类别+字段 | `resolver._load_rules()` 加载规则实例 |
| 类别 `name_source=term_base` 按术语集字段值动态生成类别 | 规则 `params.term_refs` 引用术语集做动态校验/归一化 |
| 类别 `query_sources`（label/group_field/value_field） | 规则 `params.term_refs`（label/term_base_id/group_field/value_field） |
| 类别节点按 `category_id` 绑定 Prompt | 规则 `scope` 按 `category_id`/`field_id` 绑定 |
| 三级回退：类别模板 → KB 模板 → 内置 | 三级回退：字段/类别绑定 → KB 规则 → 内置注册表 |

### 6.2 规则如何引用术语集（数据模型）

规则的 `params` 支持 `term_refs` 引用术语集，结构与 Schema 类别 `query_sources` 一致：

```json
{
  "term_refs": [
    {
      "label": "item术语集",        // 自定义别名，供 UI 展示与占位符引用
      "term_base_id": "xxxx",       // 术语集 ID（手动/api/db 三者皆可）
      "group_field": "分类",        // 分组字段（可选，用于按类别过滤，对齐 query_sources.group_field）
      "value_field": "NAME",        // 取值字段（使用新表头别名或原始字段名）
      "aliases": true               // 是否把别名/同义词并入匹配值
    }
  ]
}
```

- 规则实现从 `term_refs` 取 `term_base_id` 定位数据源，用 `group_field`/`value_field` 决定如何取值。
- `value_field` 优先按术语集 `column_aliases` 的新表头名匹配，无别名回退原始字段名 / 内置字段（manual 类型回退 `term_name` 等）。
- 与 Schema 类别复用**同一套术语集选择器**（级联到字段），保证交互一致。

### 6.3 TermBaseValueLoader（动态加载器）

新增 `services/extraction/rule_engine/term_base_loader.py`，负责按需加载术语集数据并缓存：

- **加载**：按 `term_base_id` 分页读取 `kb_terms`（`page_size ≤ 100`，循环累加到 `total`，避免校验失败），manual 类型提取内置字段，api/db 类型读取 `extras[field]`。
- **分组**：按 `group_field` 值分组，得到 `{group_value: {field: [value...]}}`，供按当前类别过滤。
- **缓存**：进程内 `{term_base_id: {version, fields: {group: {field: [values]}}}}`，依赖术语集版本号失效；并发安全（`asyncio.Lock`）。
- **分组过滤**：当规则绑定到 term_base 类别、且术语集配置了 `group_field` 与分组值时，仅加载匹配当前类别的分组数据（对齐 PromptEditor 的过滤逻辑）。

### 6.4 组装与执行时序（rule_engine）

```
对每个 category：
 1. resolver._load_rules() 解析 KB 规则实例（含 scope）
 2. rule_engine.resolve() 三级回退，得到该类别生效的规则集与 params
 3. 收集所有 enabled 规则的 term_refs
 4. TermBaseValueLoader 按 term_base_id 按需加载术语集数据（按类别分组过滤）并缓存
 5. 按 stage + sort_order 顺序执行：归一化 / 方法年代号 / 温度修正 / 跨类校验 / 去重
    - 校验类规则用术语集值做枚举/必填/一致性判定
    - 归一化/跨类用术语集 value_field 做匹配与白名单
 6. 未配置术语集的规则 → 降级跳过（保留 LLM 原值）
```

### 6.5 降级策略

- 引用的 `term_base_id` 不存在或术语集为空 → 该规则**跳过**并告警，不阻断抽取。
- 无 `group_field` 的术语集 → 全量值参与，不做类别过滤。
- 未配置任何规则 → 回退内置默认（现有 4 后处理 + 1 校验，行为不回归）。

## 七、API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/kbs/{kb_id}/extraction-config/rules` | 列出规则（含内置注册表 + 已配置实例） |
| PUT | `/kbs/{kb_id}/extraction-config/rules/{rule_key}` | 保存/更新规则（editor+） |

> 由现有 `/extraction-config/rules`、`/validation` 两个端点合并为 `/rules` 统一端点，`stage` 区分。

## 八、前端交互设计

抽取配置页签由「抽取规则 / 验证规则」合并为**「后处理与校验规则」页签**：

```
页签 N 后处理与校验规则
├─ 顶部：规则组切换（后处理 / 校验）
├─ 规则列表（卡片）
│   ├─ 名称 + 阶段 Badge + 内置/自定义标识
│   ├─ 启用开关（editor）
│   └─ 作用域 Badge（全局 / 类别@xxx / 字段@xxx）
├─ 添加规则：从规则库（注册表）选择 → 动态表单填参数 + 选作用域
├─ 行内编辑：参数表单（按 params_schema 渲染）
└─ 类别/字段选择器：级联选择（复用 Schema 模板类别树 + 字段树）
```

**作用域绑定交互**：新增规则时选择作用范围（全局 / 某类别 / 某字段），类别/字段用级联选择器，与 Prompt 模板按类别配置一致。

## 九、与既有体系的关系

- **版本管理**：`kb_rules` 纳入全量 JSON 快照，随「版本管理」页签快照/回滚/复用。
- **领域切换**：apply-template 时按 `template_code` 注入默认规则集（如材料检测默认启用温度/归一化/跨类，通用 QA 默认全关）。
- **Hook 兼容**：规则化覆盖通用场景；无法用规则表达的特殊逻辑仍走 `kb_hooks` 的 `post_process`。
- **内部字段修正**：`to_dict()` 需过滤 `_` 开头内部键，避免 `_normalize_* / _unverified / _reject_reason` 泄漏到最终结果（设计内一并修复，不影响规则模型）。
