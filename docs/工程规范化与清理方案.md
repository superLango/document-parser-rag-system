# 工程规范化与代码清理方案

> 目标：将 HansonDOC RAG 整理为符合生产级标准的工程结构 ——
> ① 剔除无用/冗余/过期引用与解释型注释；② 建立有层级的规范目录结构，消除零散存放。
> 本文为方案，**执行前需确认**。

## 一、现状问题诊断

| 文件 | 消费者 | 建议归入 |

### 1.4 extraction/ 平铺文件（未按子域归位）
`app/services/extraction/` 根目录同时存在平铺文件与子目录（`category/` `llm_extract/` `retrieval/` `rule_engine/` `prompts/`），部分平铺文件应归入对应子目录：

| 平铺文件 | 建议归入 | 依据 |
| --- | --- | --- |
| `llm_client.py` | `llm_extract/` | 仅抽取 LLM 调用 |
| `query_embedder.py` | `retrieval/` | 检索前向量编码 |
| `result_writer.py` | `llm_extract/` | 抽取结果写出 |
| `schema_builder.py` | `category/` 或 `llm_extract/` | 需最终确认 |
| `extraction_config.py` | 迁移至 `extraction_config/` 子包 | 与新配置中心并存冗余 |
| `extraction_models.py` | 保留（顶层共享模型） | 被多模块引用 |
| `extraction_pipeline.py` | 保留（主编排入口） | 被 task 引用 |

### 1.5 api/v1/endpoints/ 新旧端点并存
- `knowledge_base.py`（`/kb` 旧端点，仍被前端 `api/generated.ts` 引用）、`kbs.py`（`/kbs` 新端点）职责重叠。
- `extraction_config.py` 与 `extraction.py` 职责相近。
- 说明：删除端点存在前端兼容风险，**不建议直接删除**，列为"后续迁移项"，本次仅保留现状并记录。

### 1.6 解释型/备注型注释
- 大量模块 docstring 含「方案 §x.y」「历史备注」「流程解说」「TODO/临时」等非必要内容（如 `extraction/__init__.py` 中的 `phase2_category/`、`prompts/: YAML 模板` 等过时描述）。
- 本次将按"代码注释规范"统一清理：保留必要的 API 文档（参数/返回/异常），删除解释型、历史型、过时描述型注释。

## 三、清理清单（剔除内容）

1. **过期迁移脚本**：`alembic/versions/005_datasets.py`（引用已删除的 KbDataset 模型）。
2. **未引用/过期引用**：清理指向已删对象（sm_*/KbDataset/doc_info/热处理等）的残留 import 与注释。
3. **解释型注释**：按规范清理各模块 docstring 与 `#` 注释中的历史/解说/过时描述。
4. **冗余导出**：`extraction/__init__.py` 中对旧 `extraction_config.py` 的冗余导出。
5. **冗余/未用代码**：经引用验证确认的死代码（本次先列清单，执行时逐项确认）。

## 四、执行计划（分阶段，每阶段可独立确认）

- **阶段 0（只读）**：精确盘点所有冗余/死代码/过期引用/解释型注释清单（逐文件）。
- **阶段 1（低风险清理）**：根目录脚本归位、测试脚本归位、删除过期迁移脚本、清理注释与冗余导出。
- **阶段 2（目录重构）**：services/infra 抽取、extraction 子目录归位、更新全部 import、运行测试验证。
- **阶段 3（文档与验证）**：更新文档、全量回归（启动后端 + 跑 tests + 前端构建）。

---

## 五、风险与约束

1. **目录重构为破坏性操作**：涉及大量 `import` 修改，必须逐阶段执行并在每阶段后运行 `backend/tests/` 与后端启动验证，避免一次性大规模重构导致难以定位的回归。
2. **端点不删除**：`/kb` 旧端点仍被前端引用，本次仅记录不删除，避免前端破坏。
3. **迁移脚本谨慎**：删除过期迁移可能影响已有数据库迁移链，执行前需确认 005 是否已应用。
4. **命名规范**：文件夹/文件统一小写下划线（snake_case），Python 模块一致；组件文件 PascalCase（Vue）；常量大写。
