# 抽取配置改造方案（配置驱动补全 + 引擎重命名）

> 版本：v1.0（待确认）
> 范围：v3 结构化抽取流程（OCR 结果入向量之后 → Phase 2/3/4 → 规则引擎）
> 状态：**方案待确认，确认后实施**

---

## 1. 背景与目标

当前 v3 抽取流程中，大量参数仍为**硬编码**或**死配置**（defaults 有定义但无代码消费），未真正纳入抽取配置中心的配置项。目标：

1. 将未走配置的参数**全部纳入配置体系**，按"服务/资源级"与"抽取业务策略级"分流归位。
2. 抽取引擎（原 `glmocr` / `langextract`）**全局重命名**为 `BaseExtract` / `LangExtract`，并在抽取配置中按引擎分组独立配置参数，通过选择引擎切换。
3. 已下线的内置后处理（`post_processor` / `cross_validator`）**保留代码作参考**，不新增配置区块。

---

- **A** = 资源与配置（`kb.config.extraction`）

- **不动** = 已生效，不改
- **剔除** = 不用配置（失效）
- **参考** = 保留代码，不入配置

## 3. 引擎全局重命名（BaseExtract / LangExtract）

### 3.1 范围界定（重要）

重命名**仅限"抽取引擎"**，**不涉及 OCR 引擎**（GLM-OCR 是模型名，`GLMOCR_*` 环境变量、`ocr_config`、`ocr_util`、前端 OCR `engine: 'glmocr'` 等**一律保留**）。

| 类别 | 处理 |
|------|------|
| 抽取引擎名（配置值）`engine: "glmocr"` / `"langextract"` | 改为 `"BaseExtract"` / `"LangExtract"` |
| 抽取器类名 `GlmOcrExtractor` | 改为 `BaseExtractExtractor` |
| 抽取器文件 `glmocr_extractor.py` | 改为 `base_extract_extractor.py` |
| 抽取器类名 `LangExtractExtractor` | **保留**（已是 `LangExtract`） |
| 抽取器文件 `langextract_extractor.py` | 改为 `lang_extract_extractor.py`（可选，见 3.3） |
| 引擎专属 settings `EXTRACTION_V3_LANGEXTRACT_*` / `EXTRACTION_V3_GLMOCR_*` | 保留环境变量名，仅作为**默认值来源** |
| OCR 引擎 `GLMOCR_*` / `ocr_util` / 前端 OCR engine | **不改** |

### 3.2 改动清单

**后端（值/判断）**
- `extractor_factory.get_extractor`：`_engine == "langextract"` → `== "LangExtract"`；`"glmocr"` → `"BaseExtract"`。
- `extraction_config.py`（`ExtractionDomainConfig`）：`extraction_engine` 判断、`fallback_to_glmocr`、`effective_category_concurrency` 中的引擎名分支。
- `config.py`：`EXTRACTION_V3_EXTRACTION_ENGINE` 默认值 `"glmocr"` → `"BaseExtract"`，注释同步。
- `defaults.py`：`llm.engine` 默认值 `"glmocr"` → `"BaseExtract"`。

**后端（类/文件）**
- `glmocr_extractor.py` → `base_extract_extractor.py`，类 `GlmOcrExtractor` → `BaseExtractExtractor`，`_engine_name = "glmocr"` → `"BaseExtract"`，更新 docstring。
- `extractor_factory.py` 导入语句同步。
- `schema_builder.py` 注释同步（可选）。

**前端**
- `ExtractionConfig.vue`：`defaultLlm.engine`、下拉选项值 `glmocr→BaseExtract`、`langextract→LangExtract`（label 分别显示 `BaseExtract` / `LangExtract`）。

### 3.3 文件名是否重命名（投资决策）

- `BaseExtractExtractor` 类名**必须改**（用户明确全局改）。
- 文件 `glmocr_extractor.py` → `base_extract_extractor.py`：**建议改**，保持类名与文件名一致。
- 文件 `langextract_extractor.py` → `lang_extract_extractor.py`：类名已是 `LangExtractExtractor`，文件名仅从全小写 `langextract` 调为 `lang_extract`，**收益低、风险高**（import 面广），**建议保留原文件名**，仅改类名与配置值。

> ⚠️ 待确认：文件名是否一并重命名，还是仅改类名与配置值。

## 4. 配置结构改造（llm.engine + llm.engines.*）

### 4.1 新结构（defaults.py `DEFAULT_EXTRACTION_CONFIG`）

```python
{
  "retrieval": {
    "top_k": 20, "per_dim_top_k": 30, "weights": {...},
    "default_confidence_threshold": 0.35,
    "context_top_k": 20,          # #14 消费
    "context_max_tokens": 28000,
    "chars_per_token": 1.5,        # #15 新增
    "phase2": {"top_k": 5, "per_dim_top_k": 10},      # #11 新增
    "query_embed": {               # #17 新增
      "content_max_chars": 2000, "max_items": 15, "max_methods": 5,
      "path_items": 8, "path_methods": 3, "feature_repeat": 2,
      "embed_max_length": 2048, "type_query": "表格 数据结构 行列"
    },
    "reranker": {"enabled": True, "model": "", "top_n": 15}  # #16 消费 enabled
  },
  "llm": {
    "engine": "BaseExtract",        # 引擎选择
    "engines": {
      "BaseExtract": {
        "temperature": 0.0, "top_p": 0.1, "top_k": 20,
        "max_tokens": 32768, "timeout": 300,
        "enable_thinking": False,
        "concurrency": {"max_concurrency": 24, "cross_category": 24, "within_category": 1},
        "batch": {"single_threshold": 8000, "batch_chars": 6000,
                   "overlap": 500, "context_truncate": 32000}
      },
      "LangExtract": {
        "temperature": null, "top_p": null, "top_k": null,
        "max_tokens": 32768, "timeout": 300,
        "enable_thinking": False,
        "passes": 1, "context_window_chars": 200000, "max_char_buffer": 100000,
        "max_workers": 3, "max_examples": 3,
        "fence_output": False, "format_type": "JSON",
        "prompt_validation_level": "WARNING",
        "concurrency": {"max_concurrency": 24, "cross_category": 8, "within_category": 3}
      }
    }
  },
  "term_query": {"dedupe_keep_top_k": 5},   # #18 消费
  "kb_tool": {                                # #19 新增：脚本工具性能参数
    "embed_batch_size": 32,                  # embed 分批次大小（对应内置后处理 _BATCH_SIZE）
    "search_concurrency": 10,                # 语义检索/匹配并发上限（对应内置后处理 Semaphore）
    "semantic_top_k": 5,                     # semantic_search 默认 top_k
    "match_top_k": 1,                        # match_record 内部检索 top_k
    "match_threshold": 0.90                  # match_record 默认相似度阈值
  }
}
```

要点：
- **无 `llm.global`**——所有参数都进 `llm.engines.*`，各自独立。
- 引擎专属参数默认值来源：`BaseExtract` ← `EXTRACTION_V3_GLMOCR_*` + `EXTRACTION_V3_*`；`LangExtract` ← `EXTRACTION_V3_LANGEXTRACT_*`。
- `LangExtract.temperature` 为 `null` 时回退 `BaseExtract.temperature` 或全局默认，解决"引擎温度无法区分"。

### 4.2 与旧结构对比

| 旧 | 新 |
|----|----|
| `llm.engine: "glmocr"` | `llm.engine: "BaseExtract"` |
| `llm.temperature/top_p/top_k/max_tokens/timeout`（顶层） | 按引擎归入 `llm.engines.BaseExtract.*` / `llm.engines.LangExtract.*` |
| `llm.concurrency.*`（顶层） | 按引擎归入各自 `concurrency` |
| `llm.batch.*`（顶层） | 仅 `BaseExtract.batch` |
| `llm.engine` 与 `langextract_*` 无配置字段 | `llm.engines.LangExtract.passes/context_window_chars/max_char_buffer/max_workers/max_examples` |

## 5. 各配置项接入点详情

### 5.1 放"资源与配置"（A）：LLM 端点三元组

| 字段 | 位置 | 默认值来源 | 接入点 |
|------|------|-----------|--------|
| `api_base` / `api_key` / `model_id` | `kb.config.extraction`（已有字段） | `EXTRACTION_API_BASE/KEY/MODEL_ID` | `llm_client` 改为从 extraction 节读取 |

**架构前提（必须先行）**：v3 pipeline 当前只加载 `ExtractionDomainConfig`（来自 `kb_extraction_config`），**不读 `kb.config`**。需在抽取任务入口（`extract_v3_task`）通过 `kb_config_loader.load(...)` 加载 `KBConfig`，将 `extraction` 节合并/旁路传给 pipeline。

**llm_client 改造**：由模块级单例改为 **per-KB client 池**：
- 以 `(base_url, model, api_key)` 为 key 缓存多个 `AsyncOpenAI` 实例（懒创建）。
- `chat/chat_json` 增加可选 `cfg` 参数，从 `kb.config.extraction` 取端点。

### 5.2 放"抽取配置中心"（B）：后端接入点

| # | 配置项 | 接入文件/位置 |
|---|--------|--------------|
| 2/3/5/6/7 | LangExtract 引擎参数 | `langextract_extractor.py`：`_build_config` 从 `cfg.llm.engines.LangExtract` 读；`_extract_sync` 采样参读引擎分组 |
| 4 | 抽取并发 | `extraction_pipeline.py` / `ExtractionDomainConfig.effective_category_concurrency` 读引擎分组 `concurrency` |
| 11 | Phase2 `top_k/per_dim_top_k` | `category_builder.py`：`_PHASE2_TOP_K`、`per_dim_top_k = _PHASE2_TOP_K*2` 改为读 `retrieval.phase2` |
| 14 | `context_top_k` | `context_assembler.py`：拼接前按该数截断参与块数（默认 20） |
| 15 | `chars_per_token` | `context_assembler.py`：`_CHARS_PER_TOKEN` 从 `retrieval.chars_per_token` 读 |
| 16 | `reranker.enabled` | `reranker.py`：判断从 `settings.rerank_enabled` 改为读 `retrieval.reranker.enabled` |
| 17 | `query_embed.*` | `query_embedder.py`：模块常量改为实例属性，从 `retrieval.query_embed` 注入 |
| 18 | `dedupe_keep_top_k` | `category_builder.py`：Phase 2 query 术语集去重后保留 top_k |
| 19 | kb_tool 性能参数 | `script_tools.py`：`KbScriptTools` 构造时注入 `kb_tool` 配置；`embed` 按 `embed_batch_size` 分批，`semantic_search`/`match_record` 用共享 `Semaphore(search_concurrency)` 限并发，`semantic_top_k`/`match_top_k`/`match_threshold` 作为默认值 |

### 5.3 特殊说明

- **#9/#10 剔除**：doc_info / heat_treatment 检索参数不再全局配置，由 **Schema 模板创建类别时**的类别级 `top_k / context` 设置决定。
- **#16 reranker**：`reranker_service` 已删除（`reranker.py` 中 `reranker_service=None`）。enabled 接入后**重排仍降级为直接截断**，需另行恢复跨编码器实现才真正生效。**本轮仅接配置，不恢复重排**。
- **#19 kb_tool 配置化**：新增 `kb_tool` 区块，将脚本工具的性能参数（embed 批次、检索并发、top_k、threshold）配置化；`KbScriptTools` 构造时注入，脚本引擎调用 `embed`/`semantic_search`/`match_record` 时生效。默认值对齐内置后处理现值（32/10/…）。**注意**：`embed_batch_size` 与 `search_concurrency` 仅影响脚本工具的性能（耗时/吞吐），不影响抽取结果正确性；无脚本调用时不产生任何影响。
- **#20 参考**：内置后处理 `post_processor`/`cross_validator` 阈值（温度>100/<0、室温关键词、白名单相似度 0.90）保留在代码中作参考，不新增配置区块。

## 6. 存量数据兼容与迁移

已有 KB 的 `kb_extraction_config.content` 可能存有旧结构（`llm.engine="glmocr"`、`llm.temperature` 顶层字段等）。迁移策略：

| 层 | 方案 |
|----|------|
| **读取兼容** | `resolver` / `ExtractionDomainConfig` 读取时：`llm.engine` 若为 `"glmocr"`/`"langextract"` 映射为新名；顶层 `llm.temperature/concurrency/batch` 若存在，映射进对应引擎分组 |
| **前端兼容** | `ExtractionConfig.vue` `loadGlobal` 时做同样的旧→新映射，前端保存后即落新结构 |
| **DB 迁移脚本** | 可选：提供一次性脚本将存量 `content.llm` 旧结构迁移为新结构（幂等） |

> ⚠️ 待确认：是否需要 DB 迁移脚本，还是仅靠读取/前端保存时兼容即可。

## 8. 落地顺序

1. **引擎重命名**（`BaseExtract`/`LangExtract`）：`config.py` 默认值 → `extractor_factory` → `extraction_config.py` → `defaults.py` → `glmocr_extractor` 类/文件 → 前端下拉。
2. **配置结构改造**：`defaults.py` 新结构 → `resolver`/`ExtractionDomainConfig` 读取适配 → 前端 `defaultLlm` 与引擎切换 UI。
3. **#1 LLM 端点接入**（含 pipeline 加载 KBConfig 前提 + llm_client per-KB 池）。
4. **检索类接入**：#11/#14/#15/#16/#17/#18。
5. **存量数据兼容**（读取/前端映射 + 可选迁移脚本）。
6. **验证**：后端语法编译 + 前端 build + 端到端抽取。

## 9. 风险与验证

| 风险 | 缓解 |
|------|------|
| 引擎重命名破坏 import / 存量配置 | 一次性全局替换 + `grep` 复查 `glmocr|langextract`（排除 OCR）；读取兼容旧值 |
| `llm.engines` 结构变更影响存量为空配置的 KB | 默认结构进 `defaults`，深合并自动补齐 |
| LLM per-KB client 池内存/连接 | 按 `(base,model,key)` 缓存 + 懒创建 + 复用 |
| `context_top_k`/`query_embed` 接入改变召回行为 | 默认值对齐现值，仅当用户修改时才变化 |
| reranker enabled 接入但无重排实现 | 文档明确"维持降级"，开关仅透传 |

**验证命令**：后端 `python -m compileall app`；前端 `pnpm build`；手工抽取一文档对比新旧结果。
