## 1. S16 实现

### 1.1 原生表格 schema 通道
`channels/table_schema_channel.py`：
1. 输入 TableIR（列头路径、样例、行/列数）；
2. 模型输出**列描述**（每列角色 key/measure/condition/ignore、度量名、单位、比较符、条件、类别）；
3. 代码按描述展开记录（不依赖 v2 binding）；
4. 类别/度量名走 app_v3 归一化（`normalize_item`、`normalize_conditions`）。

配套：
- `channels/llm_client.py`：OpenAI-compatible 客户端（DSH 代理 192.168.1.35:9989）；
- `channels/instruction_table_schema.txt`：列描述 prompt；
- `tests/test_table_schema_channel.py`：展开器单测（57 passed）。

### 1.2 试点范围
- 文档：gbt-5231、gbt-3077、gjb-1951a（v2 全链路无效、缺口大）；
- 每份选 **8 张数值密度最高的表**，模型生成列描述，共 24 张表；
- 原生记录独立评测 + 与 S9 合并评测。

## 3. 分析

1. 原生通道精度高、召回低：模型给列描述→代码展开，没有 v2 的绑定错列问题；
2. 但**多余记录多**：原生通道覆盖全部列，包含大量金标未要求的条件/重复展开；
3. gbt-5231 原生记录 1378，合并后多余 2096，说明"多而不精"；
4. gbt-3077/gjb-1951a 合并后一致率仍低（0.60/0.58），主要是 v2 原记录条件错配。
5. 原生通道已证明可补匹配（+103），下一步关键是**过滤/仲裁**。
