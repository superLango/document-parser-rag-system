### D-001 K8s 验证使用本地 WSL 环境

| 项 | 内容 |
|---|---|
| 决策 ID | D-001 |
| 对应确认项 | Q1 |
| 状态 | 已确认 |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.1、[M0](M0-project-scaffold.md)、[M4](M4-sandbox-runtime.md) |

**背景**

K8s 测试/生产环境的可用性、版本与资源配置尚未完全确定，但代码层面需要一个可重复的验证环境。

**决策**

- 代码层面的 K8s 安装、配置与功能测试，使用当前本地电脑的 **WSL 环境**完成。
- WSL 内可选 k3s/kind/minikube；M0 阶段做一次 PoC，固定一种发行版并记录到本决策记录。
- 生产环境仍按 K8s 方案设计；生产集群未就绪前，以 WSL 验证结果作为代码验收依据。
- 资源配置按 WSL 实际可用资源制定最小清单；生产资源清单另行确认。

**备选方案**

| 方案 | 结论 |
|---|---|
| 直接使用生产 K8s | 不可用：环境未就绪 |
| 纯 Docker Compose | 不足：无法验证 K8s 网络/调度/隔离 |
| WSL + 轻量 K8s | 采用：成本低、可重复、能验证核心能力 |

**影响**

- M0 增加 WSL/K8s PoC 任务。
- M4 沙箱节点隔离、NetworkPolicy 需在 WSL K8s 验证。
- 生产部署前需再做一次真实集群验证。

**验证**

- WSL 内 K8s 集群可启动。
- 七个服务可部署并通过健康检查。
- 沙箱 NetworkPolicy/资源限制可验证。
- 验证步骤写入 M0/M4 文档。

### D-002 所有模型操作在模型服务器执行

| 项 | 内容 |
|---|---|
| 决策 ID | D-002 |
| 对应确认项 | Q1 |
| 状态 | 已确认 |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.2、[M2](M2-ocr-table-algorithms.md)、[M5](M5-agent-runtime.md) |

**背景**

模型服务（GLM、Qwen、Layout 等）资源占用高，且与业务服务运行环境不同。

**决策**

- 所有模型相关操作（部署、启停、参数调整、压测、日志查看）必须在**模型服务器**上执行。
- 业务服务（网关、编排、OCR 适配、Agent 服务等）不得在模型服务器上运行。
- 业务服务只通过模型 API 调用，不直接管理模型进程。

**影响**

- M2/M5 的模型调用需通过远程 API。
- 模型服务器操作需单独排期/协调。
- 本地开发使用 mock 或远程模型测试环境。

**验证**

- 业务容器内无模型进程/模型文件。
- 模型操作记录在模型服务器侧。
- 业务服务仅通过配置的 API 地址访问。

### D-003 模型三地址 + 连续 10 秒失败自动切换

| 项 | 内容 |
|---|---|
| 决策 ID | D-003 |
| 对应确认项 | Q1 |
| 状态 | 已确认 |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.2、[M5](M5-agent-runtime.md) |

**背景**

旧代码中已记录两种模型访问地址；模型服务器地址发生变更，新增 `192.168.1.35`，需要作为第三地址加入切换逻辑。单一或双地址故障仍可能导致解析中断。

**决策**

- 模型访问地址共**三个**：
  1. 旧代码记录的主地址；
  2. 旧代码记录的备地址；
  3. 新增 `192.168.1.35`（第三地址）。
- 任一地址**连续 10 秒无法连接**时，自动切换至下一个可用地址。
- 切换顺序：默认按配置顺序轮询；当前地址故障时依次尝试下一个；三个地址全部不可用时返回稳定错误码。
- 实现位置：agent-service 的 Model Gateway、OCR 服务的模型适配器。
- 切换策略：
  - 健康探测失败连续 10 秒 → 切换。
  - 切换后设置冷却窗口，避免抖动。
  - 主地址恢复后，按配置决定是否回切（默认回切，需防抖）。
- 记录 `model.failover` 事件：时间、来源、目标、原因、耗时、连续失败次数。
- M5 实现：`services/agent/model_gateway.py`；接口支持 primary/secondary/tertiary，3 地址按序切换；10 秒防抖；冷却 30 秒后回切；4xx 非 429 不切换。M6 已补齐 primary/secondary 配置（旧公网/旧局域网地址）；agent 启动与每 60 秒探测 `/v1/models`，模型名不匹配或不可达的端点标记 down，当前自动使用 tertiary。

**备选方案**

| 方案 | 结论 |
|---|---|
| 人工切换 | 不采用：故障恢复慢 |
| 单次失败即切换 | 不采用：易抖动 |
| 仅主/备两地址 | 不采用：新增 `192.168.1.35` 后需要第三地址 |
| 连续 10 秒失败、三地址轮询切换 | 采用：平衡灵敏度、稳定性与可用性 |

**影响**

- 模型网关需实现探测、熔断、三地址切换、回切。
- 需要测试：主地址故障、备地址故障、第三地址故障、双地址故障、三地址全故障、恢复回切。
- 地址与密钥通过配置注入，不写入代码/前端。
- `192.168.1.35` 只作为配置项默认值/文档记录，实际以部署配置为准。

**验证**

- [x] 模拟主地址不可达 10 秒，自动切备地址（单元测试）。
- [x] 模拟主/备均不可达，自动切第三地址（三地址 MockTransport）。
- [x] 模拟短时抖动（<10 秒），不切换 active。
- [x] 主地址恢复后按配置回切。
- [x] 三地址全故障返回 `ModelUnavailable`。
- [x] 真实 tertiary 健康与 smoke 通过；primary/secondary 已配置旧地址，当前不可达/模型不匹配，探测标记 down。
- [x] 启动/周期探测：`test_probe_marks_model_mismatch_and_unreachable` 覆盖不可达与模型不匹配。
- 报告：[M5 模型切换](reports/M5-model-failover.md)。

### D-005 并发 4 场景下选择最优上下文窗口

| 项 | 内容 |
|---|---|
| 决策 ID | D-005 |
| 对应确认项 | Q2 |
| 状态 | 已确认（默认 64K；128K 上限；并发 4 待 M8 复测） |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.3、[M5](M5-agent-runtime.md)、[窗口基准报告](reports/M5-window-benchmark.md) |

**背景**

Qwen 窗口可选 32K/64K/128K；窗口越大，上下文越完整，但显存/内存与延迟成本越高。

**决策**

- 在**并发数为 4**的场景下，结合 GLM、Layout 等其他模型共同运行的实际负载，选择性能与资源占用最优的窗口。
- 候选：32K / 64K / 128K。
- 基准指标：吞吐、p95 延迟、显存/内存、失败率、截断率、输出质量。
- **M5 实测结论：默认 64K；128K 作为上限保留。**
- 最终窗口值在 M5 基准完成后写入本记录，并更新配置默认值：`AGENT_CONTEXT_WINDOW=65536`。

**M5 实测（单请求，与 GLM-OCR/Layout 共跑）**

| 目标窗口 | 实际 prompt tokens | 延迟 | 请求后可用内存 |
|---|---:|---:|---:|
| 32K | 31,995 | 11,518 ms | 29,146 MiB |
| 64K | 63,955 | 10,054 ms | 约 29.1 GiB |
| 128K | 119,970 | 26,405 ms | 20,660 MiB |

- 全程看门狗 floor=4096 MiB，未触发。
- 128K 延迟与内存代价明显；64K 在延迟与完整性之间更均衡。
- **并发 4 × 三窗口 × 共跑模型**的组合压测尚未完成，留待 M8 负载测试；当前 M5 以单请求数据作为默认值依据。

**备选方案**

| 方案 | 结论 |
|---|---|
| 固定 32K | 风险：长文档截断 |
| 固定 128K | 风险：显存/延迟过高 |
| 基准后选择 | 采用 |

**影响**

- M5 需要窗口基准矩阵（3 窗口 × 并发 4 × 共跑模型）。
- 配置 `AGENT_CONTEXT_WINDOW` 可调。
- 窗口变化需重跑上下文/截断评测。

**验证**

- [x] 三组窗口均有 benchmark 数据（32K/64K/128K；128K 实际 119,970 tokens）。
- [ ] 并发 4 下稳定、无 OOM/死机（M8 压测待补）。
- [x] 截断率 0；上下文不变量测试通过。
- [x] 结果记录到本决策记录与 [M5 窗口基准](reports/M5-window-benchmark.md)。

### D-006 测试内存看门狗

| 项 | 内容 |
|---|---|
| 决策 ID | D-006 |
| 对应确认项 | Q2 |
| 状态 | 已确认（加载 8192 MiB / 测试 4096 MiB） |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.3、[M5](M5-agent-runtime.md)、[看门狗报告](reports/M5-watchdog.md) |

**背景**

模型服务器在窗口/并发测试中可能因内存耗尽导致死机，影响其他模型与业务。

**决策**

- 测试过程中增加**看门狗监控**：
  - 周期性读取模型服务器剩余内存（SSH `/proc/meminfo`，后续可换监控 API）。
  - 阈值：模型加载期 **8192 MiB**；测试/基准期 **4096 MiB**；检查间隔 2 秒。
  - 加载期低于阈值终止刚启动的模型进程；测试期只终止测试客户端，不杀模型服务。
  - 记录内存、进程、模型、窗口、并发、时间。
- 阈值可配置（`AGENT_WATCHDOG_FLOOR_MB`、测试脚本 `--floor-mb`）。
- 看门狗同时适用于 Agent 压测、窗口基准、OCR/GLM 共跑测试。

**影响**

- 测试脚本需内置看门狗（已提供 `services/agent/watchdog.py`、`scripts/dev/model-watchdog.py`、`guarded-model-test.py`）。
- 需要模型服务器内存采集方式（SSH/agent/监控 API）。
- 阈值过低会导致测试提前终止；过高会有死机风险。

**验证**

- [x] 模拟内存下降，看门狗在阈值触发并终止进程（4 项单元测试）。
- [x] 加载 NVFP4 时 floor=8192 MiB，就绪后守护自动退出；模型服务器保持可用。
- [x] 窗口基准/真实 smoke 使用 floor=4096 MiB，最低可用 20,660 MiB，未触发。
- [x] 日志完整记录采样与触发原因。

### D-007 沙箱运行时按多维度评估选择

| 项 | 内容 |
|---|---|
| 决策 ID | D-007 |
| 对应确认项 | Q3 |
| 状态 | 已确认（M4 完成，选定 containerd + runc） |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.4、[M4](M4-sandbox-runtime.md)、[运行时评分报告](reports/M4-runtime-evaluation.md) |

**背景**

沙箱需要执行不可信配方代码，必须在隔离、开销、兼容性之间取舍。

**决策**

- 候选：containerd（runc）、containerd + gVisor、Kata Containers。
- 评估维度与权重：
  - 安全性 30%
  - 资源开销 25%
  - 与 K8s/现有架构兼容性 25%
  - 运维复杂度 20%
- **最终选型：containerd + runc 作为默认运行时**；加权得分 9.10。
- **gVisor 作为可选加固运行时**（加权 7.65）：节点注册 runsc 后通过 `SANDBOX_RUNTIME=runsc` 切换，执行契约不变；适用于后续第三方/不可信配方。
- **Kata 本期不选**（纸面 6.55，未实测）：本机无 kata-runtime/QEMU，静态包 1.02 GB 下载超时；生产多租户阶段再用 kata-deploy 在 KVM 节点池评估。
- 硬性要求（已由 Docker/K8s 配置强制）：无网络、只读 rootfs、非 root、cap drop、seccomp、CPU/内存/PID/时长限制。
- 生产 K8s 必须使用支持 NetworkPolicy 的 CNI（Calico/Cilium）；kindnet 仅用于开发。

**备选方案**

| 方案 | 特点 | 结论 |
|---|---|---|
| containerd + runc | 开销最低、兼容最好 | **采用**；隔离由 OCI 配置 + seccomp + 资源限制保证 |
| containerd + gVisor | 用户态内核、隔离强 | 保留为可选 profile；KVM 最小执行通过 |
| Kata Containers | VM 级隔离 | 本期不选；环境无法验证，运维成本高 |

**影响**

- M4 需要 PoC 环境与评分报告（已完成）。
- 运行时选择影响节点池、镜像、监控、运维：runc 无额外节点要求；gVisor 需注册 runtime；Kata 需 KVM/QEMU 节点池。
- 不影响 M0–M3 的服务骨架与执行契约。

**验证**

- [x] runc 最小执行：uid=65534、CapEff=0、rootfs 只读、网络阻断。
- [x] gVisor 最小执行：runsc 0.0~20230807.0，KVM 平台，网络阻断。
- [ ] Kata 最小执行：环境受限，未通过（记录为偏差）。
- [x] 评分矩阵与结论：见 [M4 运行时评分报告](reports/M4-runtime-evaluation.md)。
- [x] 选定运行时通过隔离/确定性/资源测试。
- [x] K8s 资源限制与 NetworkPolicy：Calico 临时集群 A/B 实测（有策略 blocked，无策略 reachable）。

### D-008 不默认导入旧数据，仅导入词典；效果达标则全量重生成

| 项 | 内容 |
|---|---|
| 决策 ID | D-008 |
| 对应确认项 | Q4 |
| 状态 | 已确认 |
| 日期 | 2026-11-11 |
| 决策人 | 项目负责人 |
| 关联文档 | [项目需求文档](requirements.md) 6.5、[M8](M8-dictionary-comparison-cutover.md) |

**背景**

旧数据规模大、格式与新架构不同；全量导入成本高，且可能把旧问题带入新系统。

**决策**

- **暂不执行全量旧数据导入**（文档、运行记录、产物等）。
- 仅可考虑导入**业务词典数据**。
- 重构完成后，将新系统解析效果与旧数据进行对比验证。
- 若新系统解析效果达标：
  - 不导入其余旧数据。
  - 全部数据在新系统重新生成。
- 若效果未达预期：
  - 输出差异报告。
  - 反馈确认具体导入范围。
  - 不预先导入。

**备选方案**

| 方案 | 结论 |
|---|---|
| 全量导入旧数据 | 不采用：成本高、带入旧问题 |
| 只导入词典 | 采用 |
| 全部不导入 | 不采用：词典是解析基础 |

**影响**

- M8 从“全量数据迁移”改为“词典导入 + 效果对比 + 切换”。
- 全量导入脚本后置，仅在效果未达标时启动。
- 旧系统/旧数据只读保留，作为对比基线。
- 新系统上线后数据重新生成。

**验证**

- 词典导入数量/编码/别名对账通过。
- 新系统 vs 旧数据对比报告完成。
- 达标结论签字；未达标则输出导入范围建议。

### D-012 当前项目人力 1 人，按串行推进

| 项 | 内容 |
|---|---|
| 决策 ID | D-012 |
| 对应确认项 | Q8 |
| 状态 | 已确认 |
| 日期 | 2026-11-11 |

| 关联文档 | [项目需求文档](requirements.md) 6.9、[整体开发计划](development-plan.md) |

**背景**

当前项目负责人力仅 1 人，无法按多角色并行推进。

**决策**

- 所有角色由 1 人兼任；模型服务器操作、业务确认等外部支持单独协调。

- 开发计划中的时间基线按多角色假设编制；M0 启动时重新基线并更新计划文档。
- 单人执行优先保证：契约、测试、文档、可回滚；不得跳过验收门禁。
- 不得为了赶进度跳过算法基准、沙箱隔离、Agent 评测、E2E。

**影响**

- M2/M3/M5 原并行假设失效。
- 时间基线需重排；外部依赖需提前协调。
- 代码评审由本人 + 自动化门禁替代；关键决策仍需记录。

**验证**

- M0 发布 v1.1 串行时间表。
- 每个里程碑按顺序验收。
- 无跳过的质量门禁。

### D-013 旧代码归档到 `legacy/`

| 项 | 内容 |
|---|---|
| 决策 ID | D-013 |
| 对应阶段 | M0 旧代码清理 |
| 状态 | 已确认 |
| 日期 | 2026-11-11 |

- 旧 CI 归档到 `legacy/.github/workflows/ci.yml`。
